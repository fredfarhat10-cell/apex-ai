# Apex AI Security Architecture

## Overview

Apex AI is built on a foundation of **zero-knowledge, client-side encryption** with a **local-first architecture**. This document provides a comprehensive technical specification of our security model, cryptographic implementations, and future roadmap for multi-device sync.

## Core Security Principles

### 1. Zero-Knowledge Architecture
- **Definition**: Apex AI has zero ability to access, decrypt, or view user data
- **Implementation**: All encryption/decryption happens client-side in the browser
- **Guarantee**: Your master password never leaves your device

### 2. Local-First Data Storage
- **Storage**: All data stored in browser IndexedDB and localStorage
- **Network**: Zero network requests for core functionality
- **Privacy**: No cloud storage, no server access, no data collection

### 3. Military-Grade Encryption
- **Algorithm**: AES-256-GCM (Galois/Counter Mode)
- **Key Derivation**: Argon2id (memory-hard, GPU-resistant)
- **Authentication**: Built-in authentication tags prevent tampering

## Cryptographic Implementation

### Key Derivation Function (KDF)

**Algorithm**: Argon2id

**Parameters**:
\`\`\`typescript
{
  time: 1,           // 1 iteration
  mem: 65536,        // 64 MB memory
  parallelism: 4,    // 4 parallel threads
  hashLen: 32,       // 256-bit output
  type: Argon2id     // Hybrid mode (data-dependent + data-independent)
}
\`\`\`

**Why Argon2id?**
- Winner of the Password Hashing Competition (2015)
- Memory-hard algorithm resistant to GPU/ASIC attacks
- Hybrid mode combines security of Argon2i with performance of Argon2d
- Makes brute-force attacks computationally infeasible even for state-level attackers

**Cost Analysis**:
- Single password attempt: ~100ms on modern hardware
- Brute-force attack: 10^18+ years for 12-character password
- GPU acceleration: Minimal benefit due to memory-hardness

### Encryption Algorithm

**Algorithm**: AES-256-GCM

**Key Size**: 256 bits (32 bytes)

**IV (Initialization Vector)**: 96 bits (12 bytes), randomly generated per encryption

**Authentication Tag**: 128 bits (16 bytes), automatically generated by GCM mode

**Why AES-256-GCM?**
- NIST-approved, FIPS 140-2 compliant
- Provides both confidentiality (encryption) and authenticity (authentication)
- Detects any tampering or corruption of encrypted data
- Hardware-accelerated on modern CPUs (AES-NI instruction set)

### Salt Generation

**Size**: 128 bits (16 bytes)

**Source**: `crypto.getRandomValues()` (cryptographically secure PRNG)

**Uniqueness**: New salt generated for every encryption operation

**Purpose**: Prevents rainbow table attacks and ensures identical passwords produce different ciphertexts

## Data Flow

### Encryption Process

\`\`\`
User Password
    ↓
Argon2id KDF (with random salt)
    ↓
256-bit Encryption Key
    ↓
AES-256-GCM Encryption (with random IV)
    ↓
Encrypted Data + Authentication Tag
    ↓
Store in IndexedDB/localStorage
\`\`\`

### Decryption Process

\`\`\`
Encrypted Data from Storage
    ↓
Extract Salt + IV + Ciphertext + Auth Tag
    ↓
User Password → Argon2id KDF (with stored salt)
    ↓
256-bit Encryption Key
    ↓
AES-256-GCM Decryption (verify auth tag)
    ↓
Plaintext Data (or error if password wrong/data tampered)
\`\`\`

## Future: Multi-Device Sync

### Architecture Overview

**Goal**: Enable secure data sync across devices while maintaining zero-knowledge guarantee

**Approach**: End-to-End Encrypted (E2EE) Cloud Sync

### How It Works

#### 1. Client-Side Encryption
- Data encrypted on device before transmission
- Master password never sent to server
- Server stores only encrypted blobs

#### 2. Server-Side Storage
- Server acts as "dumb pipe" for encrypted data
- Zero ability to decrypt user data
- Stores encrypted blobs + metadata (device IDs, timestamps)

#### 3. Device Authorization
- New devices authorized via QR code from existing device
- Encryption keys transferred peer-to-peer (WebRTC)
- Server never involved in key exchange

#### 4. Sync Protocol
\`\`\`
Device A (changes data)
    ↓
Encrypt locally with master password
    ↓
Upload encrypted blob to server
    ↓
Server notifies Device B of update
    ↓
Device B downloads encrypted blob
    ↓
Decrypt locally with master password
    ↓
Merge changes
\`\`\`

### Security Guarantees

1. **Zero-Knowledge**: Server cannot decrypt user data
2. **End-to-End Encryption**: Data encrypted from device to device
3. **Peer-to-Peer Authorization**: Keys never transit through server
4. **Forward Secrecy**: Compromised server cannot decrypt past data
5. **Audit Trail**: All sync operations logged for user review

### Implementation Roadmap

**Phase 1**: Backend Infrastructure
- Encrypted blob storage API
- Device registration system
- Sync notification service

**Phase 2**: Client-Side Sync
- Conflict resolution algorithm
- Incremental sync (delta updates)
- Offline queue for pending changes

**Phase 3**: Device Authorization
- QR code generation/scanning
- WebRTC peer-to-peer key exchange
- Device management UI

**Phase 4**: Advanced Features
- Selective sync (choose what to sync)
- Sync history and rollback
- Multi-user shared vaults (with separate encryption keys)

## Threat Model

### What We Protect Against

✅ **Brute-Force Attacks**: Argon2id makes password cracking infeasible
✅ **Data Breaches**: Encrypted data is useless without master password
✅ **Man-in-the-Middle**: HTTPS + client-side encryption
✅ **Malicious Server**: Zero-knowledge architecture prevents server access
✅ **Data Tampering**: GCM authentication tags detect modifications
✅ **Rainbow Tables**: Unique salts per encryption operation

### What We Don't Protect Against

❌ **Compromised Device**: Malware on user's device can steal data
❌ **Weak Passwords**: User must choose strong master password
❌ **Phishing**: User must verify they're on legitimate Apex AI domain
❌ **Browser Vulnerabilities**: Security depends on browser's crypto implementation
❌ **Physical Access**: Unlocked device = full access to data

### Mitigation Strategies

- **Password Strength Meter**: Real-time feedback on password quality
- **Biometric Authentication**: Future support for fingerprint/face unlock
- **Auto-Lock**: Automatic vault locking after inactivity
- **Security Diagnostics**: Continuous monitoring for vulnerabilities
- **Open Source**: All encryption code auditable on GitHub
